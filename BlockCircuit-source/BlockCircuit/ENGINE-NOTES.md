# Block Circuit 엔진 노트

## 이번 구현의 범위

P0는 178종 블록 게임의 월드 저장 구조, 메시 생성, GPU 캐시와 블록 선택 레이캐스트를 개선한 단계입니다. 이번 추가 개발은 그 위에 고정 틱 시뮬레이션, 증분 회로 계산, 편집 이력, 비행과 설정을 더합니다. 플레이 영역은 **40×28×40**, 청크 크기는 **16×16×16**으로 유지합니다.

| 단계 | 범위 | 현재 상태 |
|---|---|---|
| P0 | 청크 저장, 변경 추적, 캐시된 GPU 메시, 그리디 병합, 프러스텀 컬링, DDA, 검증·계측 | 기존 구현 유지 |
| P1 | 플레이어 주변 청크 스트리밍, 생성 작업 분산, 무한 월드 | 후속 단계; 미구현 |
| P2의 이번 범위 | 고정 60틱과 영향을 받은 회로망의 신호 갱신 | 이번 추가 개발 |
| 게임플레이 | 실행 취소·다시 실행, 충돌 비행, 회로 디버그, 설정·퀵바 저장 | 이번 추가 개발 |

청크 주소와 내부 저장소는 음수 좌표도 지원하지만 게임의 이동·설치 범위를 확장하지는 않습니다. 회로 부품은 레버·전선·램프입니다. 리피터·피스톤 같은 새 부품이나 무한 월드 스트리밍은 이번 범위에 포함되지 않습니다.

## 고정 틱과 플레이어 물리

`Program.cs`는 실행 모드를 선택하고, 게임 루프와 화면은 `Core/Game.cs` 및 기능별 부분 클래스로 나눕니다. `Core/GameClock.cs`는 렌더링 FPS와 독립적인 **초당 60틱**을 누적 시간으로 실행합니다. 한 프레임의 입력 시간을 최대 250 ms로 제한하고 따라잡기 틱도 최대 8회로 제한합니다. 초과한 시간은 버리고 `DroppedSeconds`에 기록하므로 긴 정지 뒤에 많은 시뮬레이션을 한꺼번에 실행하지 않습니다. 일시정지·라이브러리·설정·월드 불러오기에서는 누적 시간을 초기화합니다.

`Physics/PlayerBody.cs`는 입력이나 그래픽 API를 사용하지 않고 고정 시간 간격으로 걷기, 중력, 점프와 비행을 계산합니다. `Physics/CollisionSystem.cs`는 플레이어의 이동 구간과 블록을 비교하고 X·Z·Y 순서로 충돌을 해결합니다. **F**로 비행을 전환해도 벽·바닥·월드 경계와의 충돌은 유지하며, 비행 중에는 중력을 적용하지 않습니다. 높이 상한은 발 위치 기준 `World.Height + 8`입니다.

게임의 설치·광질·레버 조작과 편집 이력 명령은 시뮬레이션 틱에서 처리합니다. **F3**으로 틱과 메시 통계를, **F4**로 회로 상태와 신호 세기를 확인할 수 있습니다.

## 회로망 캐시와 변경 이벤트

`Circuits/CircuitSystem.cs`는 레버·전선·램프의 인접 관계와 연결된 부품 집합을 캐시합니다. 블록 변경과 레버 전환을 이벤트로 기록한 뒤, 영향을 받은 회로망만 평가합니다. 레버만 바뀌면 해당 연결 집합을 재평가하고, 부품 추가·제거로 연결 구조가 바뀌면 관련된 기존 집합을 나누거나 합칩니다. 같은 처리 구간의 여러 블록 이벤트는 최종 블록 상태를 기준으로 반영합니다.

연결 집합에는 면으로 인접한 회로 부품이 포함되지만 **램프는 신호를 전달하지 않는 종단**입니다. 켜진 레버가 세기 15를 내보내고 전선·램프 한 칸마다 1씩 감소하는 기존 규칙을 유지합니다. 전원 변경은 관련 셀에만 적용하며 실제 세기가 달라진 셀의 청크를 갱신 대상으로 표시합니다.

관계없는 일반 블록 편집은 회로망을 다시 계산하지 않습니다. 월드 생성·불러오기와 외부에서 공개 상태를 직접 수정한 뒤에는 전체 `Rebuild` 경로를 사용합니다. 따라서 큰 하나의 회로망 안에서 편집하면 그 회로망 전체를 평가할 수 있으며, 작업 단위는 개별 전선보다 **영향을 받은 연결 집합**입니다.

F4에는 회로망 수, 부품 수, 최근 갱신한 회로망·셀 수, 대기 이벤트, 바라보는 부품의 신호와 편집 이력 수를 표시합니다. 가까운 부품에 신호 값을 덧붙이며, 디버그의 회로망 ID는 저장되는 식별자가 아닙니다.

## 편집 이력과 설정

성공한 광질·설치·레버 전환을 최대 **128개 트랜잭션**으로 보관합니다. 받침 채굴로 함께 회수한 전선·레버도 같은 트랜잭션에 포함하며, 블록·레버 상태와 인벤토리 증감량을 함께 되돌립니다. 새 편집은 다시 실행 기록을 지우고, 성공한 월드 불러오기는 두 기록을 초기화합니다. 실패한 작업은 기록하지 않습니다. 이력은 실행 중에만 유지합니다.

실행 취소·다시 실행은 전체 변경 내용을 먼저 검사합니다. 복원할 블록이 플레이어와 겹치거나, 인벤토리 수량 또는 현재 셀 상태가 맞지 않으면 아무 변경도 적용하지 않습니다. 도구·테스트에서 저수준 `Set`으로 실제 블록을 바꾸면 충돌하는 이력을 재생하지 않도록 기록을 초기화합니다.

`Core/GameSettings.cs`는 FPS 제한, 시야각, 마우스 감도, 그리기 거리, 퀵바 8칸과 선택 슬롯을 `settings.json`에 저장합니다. 값의 범위를 검사하고 잘못된 퀵바 슬롯은 해당 기본 슬롯으로 대체합니다. 읽을 수 없는 설정 또는 지원하지 않는 버전은 기본값과 안내 메시지로 처리하며, 설정 파일이 없는 첫 실행에는 기본값을 사용합니다. 저장은 임시 파일을 쓴 뒤 교체합니다.

**F10**의 변경은 즉시 적용하고 **SAVE**는 다음 실행에도 유지하도록 기록합니다. F5와 정상 종료에서도 월드·설정을 저장합니다. 월드, 설정과 `game.log`는 같은 사용자 데이터 폴더에 있습니다. `Core/GameLog.cs`는 UTC 시각·이벤트·메시지를 한 줄씩 추가하며 로그 기록 실패가 게임을 중단하지 않도록 처리합니다.

## 월드 저장과 변경 추적

- `World/ChunkCoord.cs`: 월드 좌표를 청크 주소와 0–15의 로컬 좌표로 변환합니다. 음수는 내림 나눗셈으로 처리합니다.
- `World/Chunk.cs`: 비어 있지 않은 청크에만 4,096바이트 블록 배열을 할당합니다. 마지막 블록을 제거하면 배열을 해제합니다.
- `World/ChunkManager.cs`: 비어 있지 않은 청크를 희소 딕셔너리로 관리하고, 실제 변경이 생긴 청크의 리비전을 올립니다.
- `World.cs`: 게임의 유한 영역, 지형, 인벤토리, 회로와 저장 파일을 관리합니다.

블록을 바꾸면 해당 청크를 갱신 대상으로 표시합니다. 청크 면 경계의 블록을 바꾸면 그 면을 공유하는 기존 이웃 청크도 표시합니다. 모서리나 꼭짓점에서는 해당되는 면 이웃을 모두 표시하며, 대각선 청크는 포함하지 않습니다. 같은 블록을 다시 설정하면 리비전이 바뀌지 않습니다. 청크 자체를 제거하면 여섯 면 이웃을 갱신 대상으로 표시합니다.

메시 생성은 청크와 그 둘레 한 블록 두께의 이웃을 읽습니다. 따라서 청크 사이에 가려진 면이 중복 생성되지 않으며, 경계 블록을 캐면 옆 청크의 드러난 면도 갱신됩니다. 램프 전원 상태가 바뀔 때도 램프가 속한 청크의 외형을 갱신합니다.

## 메시 생성과 그리기

`Rendering/ChunkMesher.cs`는 그래픽 컨텍스트 없이 CPU 메시를 생성합니다. 가려진 면을 제거한 뒤 같은 재질의 인접한 면을 직사각형으로 합칩니다. 병합 키는 블록 ID, 텍스처 변형, 면 방향, 밝기, 투명도 속성과 전원 상태를 포함하므로 외형이 다른 면은 합치지 않습니다.

병합한 면의 UV는 블록 단위로 늘리고, 셰이더가 텍스처 아틀라스의 해당 타일을 반복합니다. 큰 면에서도 블록 한 칸마다 무늬가 반복됩니다. 불투명 메시와 반투명 메시는 별도로 캐시합니다. 전선과 레버는 작은 동적 모델 목록으로 처리합니다.

`Rendering/ChunkMesh.cs`는 청크의 GPU 버퍼를 보관합니다. 리비전이 바뀐 청크만 CPU 메시를 다시 만들고 GPU로 전송합니다. 기존 용량 안의 변경은 같은 버퍼를 재사용하고, 용량을 넘을 때만 더 큰 버퍼를 할당합니다. 메시의 활성 정점 수가 0이 되면 다시 쓸 수 있도록 용량은 유지하지만 그리기와 업로드는 생략합니다. 청크 제거, 월드 교체와 렌더러 종료 시 소유한 GPU 메시를 해제합니다. GPU 작업은 렌더링 스레드에서 수행합니다.

`Rendering/FrustumCuller.cs`는 카메라의 여섯 평면과 청크의 경계 상자를 비교해 화면 밖 청크의 그리기를 생략합니다. 시야 경계와 교차하는 청크는 유지합니다.

반투명 청크는 카메라에서 먼 순서로 그립니다. **청크 안의 면을 매 프레임 깊이순으로 다시 정렬하지 않으므로**, 유리 등이 겹친 복잡한 구조에서는 투명도 표시가 부정확할 수 있습니다. 불투명·반투명 메시 분리와 청크 정렬까지가 현재 범위입니다.

## DDA 블록 선택

`Physics/VoxelRaycaster.cs`는 일정 간격으로 샘플링하는 대신 광선이 다음 복셀 경계를 통과하는 지점을 계산합니다.

- 입력 방향을 정규화하므로 사거리의 단위는 월드 거리입니다.
- 시작 셀은 각 좌표의 내림값입니다. 시작 셀이 블록이면 `Hit`과 `Previous` 모두 시작 셀을 반환합니다.
- 정수 경계에서 음수 방향으로 출발하면 거리 0에서 다음 셀로 넘어갑니다.
- 여러 축의 경계를 동시에 통과하면 **X → Y → Z** 순서로 각 중간 셀을 검사합니다. 설치 대상인 `Previous`가 충돌 셀과 면으로 인접하도록 유지합니다.
- 정확히 사거리 끝에 있는 경계도 포함하며, 끝을 넘은 셀은 검사하지 않습니다.
- 0 방향, 유한하지 않은 입력, 0 이하 사거리는 충돌 없음으로 처리합니다.

## 저장 호환성

저장 시에는 청크에서 기존 **40×28×40 배열 스냅샷**을 만들고, 로드 시에는 검증한 배열을 청크 저장소로 변환합니다. 런타임의 청크 구조를 저장 파일에 그대로 노출하지 않습니다.

기존 v1/v2 저장 형식과 블록 ID를 유지합니다. v1의 기존 지형·회로·수량을 보존하면서 새 블록 170종을 128개씩 지급하고, v2의 블록 수량은 그대로 복원합니다. 새로 저장하는 형식은 v2입니다. 불러오기 실패 시 기존 월드를 유지하며, 성공 시 이전 월드의 GPU 캐시를 교체하고 편집 기록을 초기화합니다. 퀵바와 선택 슬롯은 별도 `settings.json`에서 유지합니다.

## 검증과 계측

```bash
dotnet build -c Release
dotnet run -c Release -- --self-test
dotnet run -c Release -- --engine-tests
dotnet run -c Release -- --gameplay-tests
dotnet run -c Release -- --benchmark
dotnet run -c Release -- --circuit-benchmark
dotnet run -c Release -- --engine-smoke-test
dotnet run -c Release -- --gameplay-smoke-test
```

`--self-test`의 기존 45개 검사는 게임 규칙과 저장 호환성을 다룹니다. `--engine-tests`의 41개 검사는 청크 좌표·경계 갱신, 메시 생성·병합, 컬링, DDA와 청크 저장 복원 등 엔진 규칙을 그래픽 창 없이 확인합니다. `--gameplay-tests`의 48개 검사는 고정 시간 간격, 충돌·비행, 실행 취소·다시 실행, 회로 계산과 설정 파일을 확인합니다. **총 134개 검사가 통과**했습니다.

`--benchmark`는 CPU 메시 생성과 반복 편집 작업을 수행하고 **`benchmark-results.json`**을 생성합니다. 이 결과는 해당 환경의 CPU 작업량과 메시 크기를 비교하는 자료입니다. 실제 GPU의 FPS, 프레임 지연 또는 대규모 스트리밍 성능을 의미하지 않습니다.

`--circuit-benchmark`는 회로 계산 부하를 측정하고 **`circuit-benchmark-results.json`**을 생성합니다. 회로 갱신 범위와 계산량을 비교하는 CPU 측정입니다.

`--engine-smoke-test`에는 실제 OpenGL 컨텍스트가 필요합니다. 정지 장면에서 메시를 다시 만들거나 GPU로 전송하지 않는지, 내부·경계 편집이 필요한 청크를 갱신하는지, 램프 전원 변경이 메시를 갱신하는지, 청크 제거와 월드 재로딩이 GPU 자원을 해제하는지를 확인합니다. 결과는 **`engine-smoke-results.json`**에 기록합니다.

`--gameplay-smoke-test`는 OpenGL 게임 화면에서 틱에 대기시킨 설치·실행 취소·다시 실행, 레버와 램프 전원, 충돌 비행, 설정 화면의 일시정지와 퀵바 설정 복원을 검사합니다. **`gameplay-smoke-results.json`** 및 **`gameplay-preview.png`**를 생성하며, 스모크 테스트는 사용자의 월드나 설정을 불러오거나 저장하지 않습니다.

실행 중 **F3**으로 엔진 디버그 정보를 켜거나 끌 수 있습니다. 청크·메시·업로드 통계로 정지 장면과 편집 직후의 작업량을 비교할 수 있습니다. 측정 결과는 환경마다 달라지며 Windows 배포본은 실제 Windows에서 실행 검증하지 않았습니다.

## 회로·게임플레이 측정 결과 — 2026-10-11

.NET 8.0.31에서 **독립된 회로망 60개**를 만들고 한 레버를 반복 전환했습니다. 각 회로망은 레버 1개·전선 4개·램프 1개로 구성되며 처음에는 모든 레버가 켜져 있습니다. 준비 실행 후 **200회 전환을 5번 측정한 중앙값**은 다음과 같습니다. 원본은 [circuit-benchmark-results.json](circuit-benchmark-results.json)에 있습니다.

| 항목 | 영향받은 회로망 갱신 | 독립 참조 구현의 전체 BFS |
|---|---:|---:|
| 200회 전환의 CPU 시간 | 1.2566 ms | 49.7496 ms |
| 200회 전환의 관리 메모리 할당 | 351,240 B | 4,792,040 B |

증분 측정에는 `World.Toggle`의 편집 이력 처리도 포함하며, 참조 측정은 전원 전환과 독립적인 전체 BFS를 수행합니다. 1,000회 전환에서 회로망 갱신은 **1,000회**, 관계없는 돌 블록 편집에서는 **0회**였고 최종 전원 결과는 참조 구현과 일치했습니다. 이 값은 해당 회로 배치의 CPU 측정이며 FPS 개선율을 의미하지 않습니다.

JSON의 방문 셀 카운터는 정의가 다릅니다. 증분 방식은 램프·꺼진 레버도 포함한 영향받은 집합의 셀을 세고, 참조 BFS는 큐에서 꺼낸 전원·전선 셀을 셉니다. 따라서 보고서의 방문 셀 감소율을 정확한 CPU 작업 감소율로 해석하지 않습니다.

실제 OpenGL 게임플레이 검사 **9개**가 **90프레임·75고정 틱**에서 통과했습니다. 설치와 수량 차감, 실행 취소·다시 실행, 램프 전원 복원, 충돌 비행, 설정 화면의 시뮬레이션 정지와 퀵바 저장 복원을 확인했습니다. 결과는 [gameplay-smoke-results.json](gameplay-smoke-results.json)에 있습니다.

GPU 엔진 검사도 다시 통과했습니다. 125프레임 중 118개 정지 프레임에서 메시 생성·GPU 업로드가 모두 0회였고, 내부 편집·경계 편집·전원 변경 시 필요한 청크만 갱신했습니다. 청크 제거·월드 재로딩·종료 시 GPU 자원 해제도 확인했습니다.

## P0 기준 측정 결과 — 2026-10-08

아래는 **P0 엔진 구현 당시의 기준 측정값**입니다. 후속 회로·게임플레이 변경의 성능을 나타내지 않습니다. Debian GNU/Linux 13, .NET 8.0.31에서 기본 지형의 10개 청크를 측정했으며, CPU 값은 각 방식의 준비 실행 후 **5회 측정 중앙값**입니다. 원본 수치는 [benchmark-results.json](benchmark-results.json)에 있습니다.

| 항목 | 개별 면 메시 | 그리디 메시 |
|---|---:|---:|
| CPU 메시 생성 | 6.547 ms | 4.990 ms |
| 관리 메모리 할당 | 4,402,008 B | 1,469,760 B |
| 사각형 수 | 7,768 | 2,432 |
| 정점 수 | 46,608 | 14,592 |

사각형 수는 **68.69% 감소**했습니다. 이 비교는 당시 CPU 메시 생성기의 병합 사용 여부를 비교한 것으로, 이전 게임과의 FPS 비교가 아닙니다. 시간은 하드웨어와 실행 환경에 따라 달라집니다.

CPU 캐시 검사에서 300회 정지 갱신 동안 메시 생성은 0회였으며, 내부 편집은 1개 청크, 경계 편집은 2개 청크를 갱신했습니다. 고정 시드로 2,000회 편집하고 20번 전체 메시를 새로 생성해 비교한 결과 모두 일치했습니다. 이때 캐시 메시 생성은 358회, 소요 시간은 **286.2 ms**였으며 전체 재생성과 일치 검증 시간이 포함됩니다.

실제 OpenGL 검사 **125프레임**도 통과했습니다. [engine-smoke-results.json](engine-smoke-results.json)에 기록된 118개 정지 프레임에서는 메시 생성과 GPU 업로드가 모두 0회였습니다. 내부 편집·경계 편집·램프 전원 변경은 각각 1·2·1개 청크를 갱신했고, 같은 크기의 편집은 추가 GPU 할당 없이 버퍼를 재사용했습니다. 검사 중 할당한 GPU 메시 21개를 모두 해제했으며 종료 후 남은 VBO는 0개였습니다.

기존 평면 배열 지형과 청크 지형의 바이트 배열도 일치했습니다. 회귀 검사 기준 SHA-256은 `48563C0F5486EC9E67CC186343958F2EFD814D21A25BF78921816DF12E4525D7`입니다.
